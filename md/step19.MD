# 목표
- 에이전트는 LLM을 이용하여 추론(Reason), 행동(Act)을 교차 반복하여서 문제를 자율적으로 해결 -> 인공 지능 패턴 : ReAct(Reasoning and Acting)
- 한 번의 ReAct 호출을 넘어서 결과를 검증 -> 재시도 -> 루프 구조 구성
- 제한을 두고 반복 수행 진행 (임시 -> 비용/시간 절감) -> 처리가 안 되면 Human in the loop를 같이 적용할 수 있다. 
- 질문 -> 답변 (기존), 계획 -> 실행 -> 검증 -> 부족하다고 평가 -> 수정 계획 -> 실행 ... 작동하는 agent 구성
- 이렇게 에이전트를 작동시키는 방식을 루프 엔지니어링이라고 함.  
  - 사람이 매번 프롬프트를 입력하는 대신, 목적을 정의하면 AI 에이전트가 목표를 완수할 때까지 스스로 판단·행동·검증을 반복하도록 시스템을 설계하는 방법론

## 1. 데이터 가용성 문제

현재 제공되는 refund_summary 도구는 아래와 같이 집계 데이터만 반환합니다.
- 환불 요청 건수

건별(개별 거래 단위) 상세 데이터는 제공되지 않아 정책 준수 여부를 건 단위로 판단하기 어렵습니다. 건별 데이터 제공이 가능한지, 또는 집계 데이터를 기준으로 판단을 진행해도 되는지 확인이 필요합니다.

정책 조회(RAG) 결과(문서: CS-REFUND-2026)에 따르면 에스컬레이션(정책 예외 처리)이 발생하는 기준은 다음과 같습니다: 판단이 어려운 품질 문제나 반복 분쟁 건은 임의로 처리하지 않고 CS 책임자에게 이관하며, 동일 유형의 문의가 반복될 경우 사례와 처리 결과를 기록하여향후 정책 개선과 상담 기준 정비에 활용합니다. 또한 반품 제한/환불 거절 시에는 사유를 고객에게 명확히 안내해야 한다는 절차도 명시되어 있습니다.

결론: 9월 초(2024-09-01~09-10) 환불 건 중 실제로 에스컬레이션이 발생했는지 여부는 현재 확인할 수 없습니다. 환불 데이터 조회 도구에 오류가 발생해 해당 기간의 실제 환불 사례(건수, 사유, 금액)를 가져오지 못했기 때문입니다. 다만 사내 정책(CS-REFUND-2026)상 에스컬레이션 발생 조건은 ① 판단이 어려운 품질 문제, ② 반복 분쟁 건이며, 이 경우 CS 책임자에게 이관하여 처리하는 방식이 규정되어 있습니다.
